这是"展示摄影与音乐"这个需求里的音乐半边,分两条独立轨道:

- **Track A(已在进行,不属于本文档)**:`/about` 收藏架 `shelves.music` 纯文字填空,等真实歌单,填完即完成,不需要专门的设计文稿。

**一个容易被误读的地方,先说清楚:** HOME-DESIGN §9 写过"走廊永远不再接受任何视觉组件"。本次新增的不是给走廊加组件,是走廊本来就为分期开门预留的机制(`notes`/`photos` 已经以未开放状态占着位置)新开一格——第六扇门用的是同一套"房间未开放不渲染"的既有机制(rooms.ts),不碰走廊的视觉表面。锁死条款锁的是走廊的装饰层,不是房间数量。

摄影(`/photos`)侧维持此前的排期决定:优先于 `/notes` 上线,不受本文档影响。

## 2. 精选 — 内容与机制

**定位:** 策展式、非时间序的收藏。回答"我反复回去听的是什么",不是排行榜,不是打分,也不是"最近喜欢"——是经得起反复的那一小撮。

**反默认:** 不做播放次数、播放时长这类量化展示。本站没有真实播放数据可报;伪造一个"播放 37 次"式的数字,比不放数字更假(呼应 `/about` 策展人注记的"不许假")。

**字段规格:**

```yaml
favorites:
  - title: 专辑名 或 "专辑名 / 艺人"(自由格式,不拆分成结构化的 artist 字段)
    note: 它对我做了什么,一句话,第一人称口吻(同 /about 收藏架的备注写法)
    sleeve: /reel/xxx.jpg   # 可选,见下方"封面"
    href: https://...       # 可选,外链,同 /about 收藏架处理:target="_blank"
```

`title` 不单独拆出 `artist` 字段——直接沿用 `ShelfItem`(`/about` 收藏架)已有的"一个标题字符串,信息量由你自己决定怎么写"的先例(`/about` 的书目条目同样没有单独的作者字段)。这是刻意的最小化,不是遗漏。

**类型独立性(一个技术判断):** `ReelFavorite` 不复用 `ShelfItem` 类型,而是单独定义一个结构相似、多一个 `sleeve` 字段的新类型。原因:如果给 `ShelfItem` 加 `sleeve`,`/about` 的 `books`/`gear`/`films` 也会技术上"有能力"挂封面图,这和 ABOUT-DESIGN 明确写下的"收藏架纯文字,不放封面图"直接冲突。宁可多写一个几乎一样的类型,也不让 `/about` 因为 `/reel` 的需要被悄悄松绑。

**封面(sleeve)——一处更正:** 此前我在对话里说过封面图要靠 `/photos` 的 R2 管线,这个说法错了,在这里更正。查过 `lib/content.ts` 与 `/lab` 的 `poster` 字段实现(`content/lab/001-breathing-field/index.md` 里 `poster: /lab/001-breathing-field.svg`,指向 `public/lab/` 下的静态文件,`<img src>` 直接渲染,零管线)后确认:精选封面数量少、体积小、经过挑选,完全可以照搬这条已经跑通的路——图放 `public/reel/`,frontmatter 里就是一个根相对路径字符串。R2 是 `/photos` 因为原图体积大、数量多、且 gitignore(DESIGN §4 约定 4)才需要的,`/reel` 不适用,也就不需要等 `/photos` 的管线先做完。

**美学基调(不写进字段,写在这里做实现指引):** 封面裁切建议偏方形、克制留白,呼应实体介质的"封套感"——这不是加一个 `format: vinyl` 之类的结构字段,黑胶只是一个口味参考,不是本房间要记录的数据。

**空状态:** `favorites` 为空数组时,整段不渲染——与 `now.sections`、`about.shelves` 现有的"按 `items.length > 0` 过滤"规则一致,不需要新规则。

**声音:** 无。纯陈列,不涉及播放,继承 SOUND-DESIGN 三铁律里最省事的那一条——不播放就没有铁律要管的对象。

## 3. 日志 — 内容与机制

**定位:** 时间序、诚实的流水账,回答"这段时间在听什么"。和精选是完全不同性质的记录(时间性 vs 策展性),不是精选剩下的"备选池"。

**反默认:** 不做置顶(pinning)。这是此前三个结构方案里被否决的方案 B——置顶会破坏时间序本身的诚实性,一旦有条目可以"跳队",日志就不再是日志。

**字段规格:**

```yaml
log:
  - date: 2026-08-20
    text: 一句话,这段时间在听什么、什么情境下听的(同 /now listening 小节的口吻)
    ref: /lab/002-xxx   # 可选,跨房间反链
```

**`ref` 字段——一处需要你确认的重建:** 会话记忆里提到这是此前讨论过的"跨房间反链"想法,但具体字段形状是我这次重建的,不是逐字记录。我的理解:`ref` 是站内路径字符串(如某篇 `/notes/[slug]` 或某个 `/lab/[slug]`),标注"当时在做什么",渲染成一个不抢眼的 mono 小链接(同 `RoomHeader` 返回链接的处理:`white/60`,hover 加下划线)。主要设想用在日志条目上(记录当下情境),精选条目本次没有配 `ref`——如果理解有偏差,这里是最需要你核对的一处。

**空状态:** `log` 为空数组时,整段不渲染,与 `favorites` 是否有内容互不影响——房间只要两段里任一段有真实内容就该上线,不必等两段同时填满(红线 3 的"宁缺毋滥"管的是"没内容的整段不要出现",不是"两段必须同时就绪")。

**声音:** 无,理由同 §2。

## 4. 走廊集成与两处待确认的判断

**导航词序(判断,请确认):** 建议把 `reel` 追加在 `ROOMS` 数组最后(`about` 之后),而不是插进 `lab` 与 `notes` 之间这类按语义分组的位置。理由:这个站一贯是追加式存档(记录只增不改写,签名账本按登记顺序记账),新房间的位置也该反映"什么时候被决定",而不是重新排一次语义顺序。走廊实际显示顺序由数组顺序决定、`open` 只控制是否出现,所以这个选择不影响 `/photos` 先于 `/notes` 上线的既定排期,两件事互不干扰。

**`RoomStatuses.reel` 读数形态(判断,请确认):** 建议 `{ favorites: number, logEntries: number } | null`,仿照 `lab` 现有的计数式读数(`{ experiments, ongoing }`)。没有内容时整体为 `null`,门缝读数那一行照既有规则省略。

**`getLatestEntry()` 全站联动——特意不做:** 这个函数目前专门服务走廊主页的"最新记录"读数,注释里写着是为 `notes`/`photos` 上线预留的。要不要把 `/reel` 日志的最新一条也算进这个全站读数,是一个会改变走廊主页行为的决定,不该被一个房间切片顺手带过——这不属于本次范围,想做的话建议另开一次 HOME-DESIGN 层面的讨论。

## 5. 视觉、间距与降级

- **精选:** 卡片流,`sleeve`(可选)+ `title` + `note`(+ 可选 `href`,`target="_blank"`,同 `/about` 收藏架现有处理)。`sleeve` 加载失败或缺失时优雅降级为纯文字卡,不留破图占位。
- **日志:** 纯文字流,`date` + `text`(+ 可选 `ref`)。字号字重不做层级——继承 §DESIGN 2 的铁律,灰阶只分工位置不分内容重要性。
- **间距:** 精选块与日志块之间用"块级"间距,参照 `/now` 页面 `sections` → `paragraphs` 之间的既有节律(不同性质内容块之间留更大的呼吸);块内条目沿用 `/now` 列表条目的既有节律。都是复用现成的间距阶,不新开一档。
- **动效:** 无入场动画,无 hover 增强。降级(`prefers-reduced-motion`)对本房间没有影响——本来就没有动效可关。
- **无障碍:** `sleeve` 图片 `alt` 必填(空字符串也算显式声明,不是漏填);外链遵循站内既有的可访问链接模式(真实 `<a>`,`:focus-visible` 绿色描边);颜色对比沿用现有 token(`white/70` 正文、`white/40` 仪器读数),不引入新对比度审查项。
