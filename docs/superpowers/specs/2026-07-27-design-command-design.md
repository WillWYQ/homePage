# `/design` 设计推演命令 — 设计文稿

> 2026-07-27 · willsleep.dev (myHomePage)

## 1. 要解决的问题

站点的设计文稿（`docs/DESIGN.md` 及各房间独立规格）已经很密，但推演新设计时每次都要重新建立同一套上下文：三条红线、动效四层预算、声音三法则、lab 策展三问、"只追加不重写"的档案纪律。结果是每轮对话都在复述已定案的东西，且新提案容易漂出这套约束而没人拦。

`/design` 把这套约束固化成一个可重复调用的推演流程，让每一轮设计对话从同一个起点出发，并在收口前强制过一次红线。

**它不做什么：** 不写代码，不做实现计划，不改文稿（除非用户在收口后明确点头）。

## 2. 形态

- 仓内 slash command，文件 `.claude/commands/design.md`（新建 `.claude/` 目录）。
- 调用形式 `/design <参数>`，单命令带三种模式，由参数自动判定。
- 终态是**对话中的结论**，不是文件写入。写文件是收口后一问一答的独立动作。

## 3. 模式识别

看参数的第一个词，三选一：

| 条件 | 模式 |
|---|---|
| 匹配到房间名或路由（`now` `lab` `notes` `photos` `about` `/lab` `404` `home` `/`） | **房间模式** |
| 空参数，或以 `audit` 开头（`audit` 后可跟范围，如 `audit notes`） | **审计模式** |
| 其余任意自然语言描述 | **系统模式** |

判定不确定时（例如参数同时提到房间名和跨房间话题），先问用户一句要按哪个模式跑，不自行猜。

## 4. 上下文加载

分层加载，避免每轮吞下全部 1512 行文稿。

**三种模式共同的地基（不可省）：** `docs/DESIGN.md` §1（定位与原则，含三条红线）与 §2（视觉语言：色彩、字体、动效四层预算、声音三法则、语言与文风）。

**各模式追加：**

- **房间模式：** `DESIGN.md` §5 中该房间的段落；若存在同名独立规格（`HOME-DESIGN.md` / `ABOUT-DESIGN.md` / `SOUND-DESIGN.md`）则全文读入；`COMPONENT-SOURCES.md`（知道手上现有哪些仪器）。
- **系统模式：** 先读 `DESIGN.md` 的全部小节标题建立地图，再按话题读入相关章节。
- **审计模式：** 被审范围的全部文稿全文，外加 `git log` 查看这些文稿最近的修改轨迹（判断某处是新写的还是历史遗留）。

**源码：** 一律不读。唯一例外是推演触及"这个效果现有组件能不能做得到"，此时才去 `components/` 确认可行性。

## 5. 四步推演（房间模式 / 系统模式）

每步只问一个问题，问完等用户回答，不批量抛问题。

1. **身份** — 这个房间／系统层在这栋楼里是什么？它的一句话馆训是什么？判据取自 `OBSERVER-RAW.md` 与 `ABOUT-DESIGN.md` 附录里那个人的性格，而不是"好网站通常长什么样"。
2. **形态与单元** — 内容单元是什么（record / roll / 实验 / 条目）？列表页长什么样？frontmatter 有哪些字段？空状态怎么处理？
3. **签名效果** — 这个房间唯一那一个叙事效果是什么，它在传达什么信息？**默认答案是"没有"**；提案必须先说服推演者它该存在，才进入下一步。
4. **宪法过滤** — 把前三步的产出逐条过：三条红线、动效四层预算、声音三法则、lab 策展三问（若涉及实验）、档案"只追加不重写"纪律。被枪毙的提案连同否决理由进入否决名单。

系统模式沿用同样四步，只是"房间"换成被讨论的系统层（如房间间的数据流、仪表读数语法、双语版本形态）。

## 6. 审计模式

四步反向跑在现有文稿上：读入范围内文稿，逐段对照宪法与彼此，找出偏离。

**每条发现必须包含：**

- 文件路径 + 行号
- 问题分类，四选一：`自相矛盾`（两处文稿打架）／ `自我感动`（写得漂亮但没有实际约束力或读者感知不到）／ `无法施工`（描述不足以让人写出代码）／ `与红线冲突`
- 一句话说明问题
- 建议的修正方向（一句话，不展开成新设计）

**只报不改。** 审计不直接编辑文稿，输出后等用户挑选哪几条要修。

## 7. 输出格式

推演收口时给出两块内容：

**已定案决议** — 编号列表，每条一句话，措辞与现有文稿同构（可直接粘进 `DESIGN.md` 或独立规格）。

**否决名单** — 提案 + 否决理由，对应 `HOME-DESIGN.md` §9 那种记录形式。否决要留名：记下被否的是什么、为什么否，而不只是"不做"。

末尾问一句是否写入文稿，并给出建议落点（新建 `docs/XXX-DESIGN.md` ／ 更新 `DESIGN.md` 某节）。用户点头后才动文件，动完提交，git 历史即设计史。

## 8. 边界

- 不进入实现：不写组件、不改 `app/`、不提实现计划。用户要施工时那是另一条路径。
- 不做无关重构提议：推演只服务当前话题。
- 未上线房间不因推演而在走廊出现门牌（红线 3 归红线 3，推演产出文字不等于上线）。
